2. Canonical direction for `asym-GL`: frontend should match backend. The backend is the model actually optimized and serialized into `fitted_y` ([fitting.py](/Users/skyefortier/xps-app/fitting.py:1190), [fitting.py](/Users/skyefortier/xps-app/fitting.py:1257)). Changing backend would change fit semantics and downstream parity. Literature check: CasaXPS/Fairley-family asymmetric standards are DS, DL/split-Lorentzian, and LA/LF/LX-style asymmetric Lorentzian plus Gaussian convolution, not this frontend's unbounded distance-growing width. CasaXPS LA is exponent-based with Gaussian convolution; Major et al. describe LA/LF exponents and DL as joined Lorentzian halves. Backend `asym-GL` is defensible as an empirical split-width pseudo-Voigt, but it is not CasaXPS LA. Do not silently replace it with LA/DS in this fix.

3. Backend continuity: no value or first-derivative discontinuity at `x = center`. Both Gaussian and Lorentzian components have zero slope at their maximum, independent of width, so the two half-width branches meet at amplitude with left/right derivative 0. The second derivative jumps when asymmetry is nonzero, but that should not meaningfully destabilize lmfit; it is C1, not C2.

Bounds mismatch: backend clips/effectively bounds `asymmetry` to `[0, 1]` in the function and lmfit params ([fitting.py](/Users/skyefortier/xps-app/fitting.py:90), [fitting.py](/Users/skyefortier/xps-app/fitting.py:923)). Frontend input declares `min=0 max=1` ([templates/index.html](/Users/skyefortier/xps-app/templates/index.html:5761)), but `updatePeakParam` directly assigns the parsed value ([templates/index.html](/Users/skyefortier/xps-app/templates/index.html:5494)). So pasted/loaded/programmatic values can exceed backend semantics until a backend fit result overwrites them. Local JS fitting clamps asymmetry to `[0, 0.9]`, which is another small inconsistency ([templates/index.html](/Users/skyefortier/xps-app/templates/index.html:6918)).
