## 1. The seal — one deep-frozen object per fit, tagged by engine

`fitResult.seal = deepFreeze({v: 'xps-seal-1', engine: 'server' | 'local', producer, R, O, D, E})`.
`producer`: 'runFit' | 'useSolution' | 'autoFit' (server) / 'local' | 'batch' (local).

**R (both engines) — what the fit was made from, captured synchronously before the first await:**
- `pageModel` — a deep copy of the peak objects the fit STARTED from, every own field (Run Fit: the
  live peaks; "Use this solution": `opts.startPeaks`; Auto-Fit: each fit's built model with its
  `_af*` overlays; Batch: the target's peaks after propagation and scaling);
- `context0` — ONE record of the context, in two parts:
  - `live` — every field with a LIVE per-tab control that bears on the fit: the `_STARTS_UI_FIELDS`
    (bg type, bg start / end, Shirley iterations, endpoint averaging, ROI min / max), the fit method
    (`fitMethod`, made a per-tab workspace field, §8.5), the charge-reference controls (`ccMethod`,
    `ccObs`, `ccLit`, already captured per tab by `_captureUI`), the manual anchors, and the shift in
    force (`ccShift`, required finite — a producer refuses a non-finite shift, since `_roiSelect` reads
    NaN as 0);
  - `producer` — what has NO live control: `n_perturb` (the page's constant), `n_starts` (derived from
    the model), `require_component` (Auto-Fit), the local engine's options. Bound by step 0 / the local
    input reconstruction only, never by the live key.
  Every reference below to the shift or the ROI means `context0.live.ccShift` / `context0.live.roiMin
  / roiMax`;
- `idx` — the indices `_roiSelect(rawBE, rawIntensity, context0.ccShift, context0.roiMin/Max)`
  returned; `energies`, `counts` — the arrays the fit received (server: exactly what
  `uploadToBackend` sent; local: the corrected energies and raw intensities of `idx`);
- `page` — the producing page's identity: the `xps-software` and `xps-page` meta contents
  (`page_sha256`, `reference_sha256`).
- server only: `request` — the wire body exactly as sent, `session_id` removed (transport).
There is no separate `R.roi` / `R.ccShift`: both are read from `context0` (one source; review B1).

**O** — server: the `/api/fit` reply verbatim. Local (V6.7, §6.4): `{engine: 'local', energies, net,
background: {values, certificate, effect}` (ordinary fields, not array properties), `weights`,
`paramMap`, `model` (the frozen final snapshot), `curves`, `modelSum`, `chi2`, `chi2r`, `rmse`,
`rFactor`, `areas`, `iterations`, `certificate`, `support`, `success: true`, `reportable: false}`.

**D** — `{chosenAlternative}` ("Use this solution": the alternative's description, attributed
history); otherwise `{}`. Auto-Fit's finalisation is not a D step since Q8 (it refits).

**E** — Auto-Fit only: the anchor fit's `{R, O}` (same server schema), judged in §6.3.

## 2. One context binding (V6.4)

From `R.context0` alone the page derives, and requires EXACTLY:
1. `ccShift` finite; `_linkGraphFailure(R.pageModel)` null.
2. **Samples:** `_roiSelect(tab.rawBE, tab.rawIntensity, context0.ccShift, context0.roi*)` → `R.idx`
   element for element; `R.energies[j]` = that reader's corrected energy, `R.counts[j]` =
   `tab.rawIntensity[R.idx[j]]` (server: `O.energy` / `O.counts` = R's; the server checks too).
3. **Step 0, by engine.** SERVER: `_buildFitRequest(producer, R.pageModel, context0, R.energies)` — the ONE pure builder
   the producer itself uses (`peakToBackendSpec`, the background payload through `_bgWindowIndices`,
   averaging as the request reads it, `context0`'s own anchors, the method, `n_perturb`, `n_starts`,
   Auto-Fit's overlays and `require_component`) — equals `R.request` exactly (key order irrelevant,
   values and presence exact: an omitted field is not an explicit null). LOCAL (no wire request): the
   input reconstruction — `O.energies` equals `R.energies`; `O.net[j]` equals `R.counts[j] −
   O.background.values[j]` in that association; `O.weights[j]` equals `1 / √max(O.net[j] +
   O.background.values[j], 1)` (the engine's own association: weights from net + background, never
   recomputed from raw counts); `O.paramMap` equals the varied-parameter inventory the engine's own
   function derives from `R.pageModel` (locks, links) and `context0.producer`'s options.
4. **Background:** the page's certified background for `R.energies` / `R.counts` under `context0`
   (`computeBackgroundCore`) equals `O.background_y` (server) / `O.background.values` (local)
   exactly, and `_bgEffect` of `context0` equals `O.background_verdict.effect` / `O.background.effect`.
5. **Display frame:** the chart's energies are `rawBE[R.idx[j]]` corrected by the LIVE shift, which
   the live binding (§3) requires equal to `context0.ccShift` — never a translation of R's energies.
A narrower `idx` paired with a wider `context0` fails 2; an inconsistent request fails 3.

## 3. The live binding

`_sealLiveKey(owner)` is a canonical key of the owner's peaks (every field `project` reads or writes,
incl. the `_af*` overlays) and EVERY `context0.live` field, read by ONE owner-aware reader
`_contextOf(owner)` (the active tab: its live controls; an inactive tab or a snapshot: its record —
`tab.ui`, `tab.ccShift`, `tab.manualAnchors`), through `_fitKeyCanon`'s readers EXACTLY as they are
(energies by `parseFloat`, counts by `parseInt` — except endpoint averaging, which keeps its
refusal-aware reader, so an invalid "1e2" never matches a valid "1"). PRESENTATION fields are not in
the key — a peak's name, colour and visibility (the fields `_STARTS_MODEL_FIELDS` excludes today):
editing them never makes a fit stale (pinned by a test), and the view shows them live (§7). The binding holds when it equals `_sealKeyOf(project(R.pageModel,
O, D), R.context0.live)`. VISIBLE CHANGE: the fit method and the charge-reference controls are now part
of the fit's context — changing either after a fit makes it stale (until today only the shift was).

## 4. `project` — the live path as a pure function (V6.3)

`project(pageModel, O, D)` (server): a deep copy of `pageModel`; per component `_applyBackendParams`'
own rules as a pure function of (copy, O's params) — a locked field keeps the snapshot's value, a free
one takes O's through the live conversion, an expression takes O's whatever the lock (Q10 0c); no
mutable object shared with the seal. ONE READING, as built (step 2, Codex rounds 1-3): the live path
keeps applying a reply with `_applyBackendParams` on the live peaks exactly as before — the same rules
`project` applies to the snapshot; a re-implemented live write set drifted on edge values in three
review rounds (a reply naming fewer components, a −0, a locked field an adopted start holds
differently). `project` is pinned to the old application on a copy of the snapshot, and the live
binding (§3) requires the live model to equal `project(...)` before a fit is CURRENT. Local: the projection is `O.model` (the frozen snapshot the engine
DERIVED FROM R, never taken from O: `projectLocal(pageModel, O)` = a deep copy of `pageModel` (its
structure: membership, order, shapes, lock flags, link graph, every non-optimised field), with ONLY the
free parameters of `O.paramMap` set to `O.model`'s values and the linked fields propagated over
`pageModel`'s link graph by the engine's own rule; it must equal `O.model` field for field (a model
whose shape, lock or link differs from the start fails — a substituted lineshape cannot pass), and
every free value lies in the engine's bounds (§6.4).

## 5. States and their presentation (V6.5 as amended)

`sealedState(fr, owner)` → `{state, check, reason, view}`, the ONLY reader of R / O / D / E:
- **CURRENT** — §2 holds, §3 holds, (Auto-Fit) §6.3 holds, and the verification (§9) answered
  `consistent` for THIS seal (local: the page's own exact check, §6.4).
- **PENDING** — §2/§3 hold, the verification is outstanding.
- **UNCONFIRMED** — §2/§3 hold, the verification answered `unconfirmed` (made under other numerics and the recomputation differs — amended 2026-10-15, below;
  non-finite, a non-bit-stable lineshape's evaluation) or the server could not be reached.
- **STALE** — §3 fails (an edit), or §2 / §6.3 fails, or the verification answered `mismatch`
  (the failed check named).
- **PEAKS-ONLY** — no usable seal (fails its schema), or a legacy fit the adapter cannot reconstruct.
- **LEGACY** — an UNSEALED fit (saved before this release): today's restore machinery decides what it
  can show; a permanent ceiling makes it never current (Q1): "saved before sealed records — re-run
  this fit to confirm" (1d).

## 6. Producers

**6.1 Run Fit.** `pageModel` and `context0` captured before the first await; the request built by
`_buildFitRequest` from them (the same function step 0 runs); `idx` / `energies` / `counts` from the

**6.2 "Use this solution".** As 6.1 with `pageModel = opts.startPeaks` (the live pre-operation model
is kept only for the ownership check); `D.chosenAlternative`.
**6.3 Auto-Fit (V6.3 step 2, the transaction).** One operation spans both fits AND both
verifications; the progress overlay stays until the commit. Before the commit the page requires:
R₁ binds to the same tab's raw data under `R₁.context0` (§2); `/api/verify-fit {R₁, O₁}` →
consistent; `O₁.success === true`; the anchor gate (`_autoFitGraphiteIsSupported`), the
reference-centre window and `O₁.required` re-derived by the same functions from O₁; `derive(R₁, O₁)`
— the projection of O₁ onto `R₁.pageModel`, every centre and manual anchor moved by −Δ, the endpoint
fields re-rounded only when Δ ≠ 0, the overlays carried, the window reselected in the new frame,
every centre locked, the producer's settings unchanged — equals `(R₂.pageModel, R₂.context0)`
exactly; `/api/verify-fit {R₂, O₂}` → consistent; `O₂.success === true` (acceptance AS RECORDED, as
the producer requires today — not proven); and O₂'s anchor still passes. The SAME predicate (both
acceptances, both verifications, gates, derivation) judges a restored Auto-Fit seal. The derivation
includes the charge-reference controls: `ccObs` = the anchor's raw centre from O₁ plus the old shift,
`toFixed(3)` (today's rule), `ccMethod` / `ccLit` as Auto-Fit sets them, and the new `ccShift` from
them — so `R₂.context0.live` is what `derive` produces, not a copy of R₁'s. STAGED verification (§9):
the two checks belong to the transaction, not to an installed seal. Restored Auto-Fit's AGGREGATE
state: any failed binding / gate / derivation, a recorded `success !== true`, or a `mismatch` → STALE;
else any check outstanding → PENDING; else any `unconfirmed` / unreachable → UNCONFIRMED; else
CURRENT. COMMIT: charge
correction, model and seal (R₂, O₂, E = {R₁, O₁}) at once, one undo entry. ROLLBACK (still owner):
any failure, including a verification that is unconfirmed or unreachable — "Auto-Fit could not be
confirmed; nothing was changed" (visible change). SUPERSEDED: nothing written. On load, CURRENT
needs E judged the same way (two verifications).

holds; the background as §2.4. Batch: each target's R after
propagation and scaling, from that target's own raw arrays and context. The starting-point

## 8. Mutators, snapshots, persistence, provenance

**8.1 Mutators.** A sealed fitResult is `{seal, view}` and frozen; `_invalidateBgCache`,
`_invalidateFittedY`, `_restampSupport`, the lazy rFactor are no-ops on it (the edit preview reads
live peaks and the live background separately, as STALE shows). LEGACY / SEALED DISPATCH IS
STRUCTURAL: every loader and restore entry branches on `fr.seal` first; `_restoredFitBgFailure` and
the rest of the restore machinery throw if handed a sealed fit.
**8.2 Undo / history / Auto-Fit snapshots.** Peak-only undo keeps the installed seal and re-judges
(undoing an edit returns CURRENT). Contextual undo, history restore and Auto-Fit rollback reinstall
the CAPTURED seal reference and rebuild its view (verification cache reused, §9). A snapshot with no
seal restores no seal.
**8.3 Provenance (G6).** `view.provenance` = ATTESTED when `O.software` (server) or `R.page.software`
(local) has a 40-hex `git_commit`, `git_dirty === false`, an `env_sha256`, and `R.page` holds
`page_sha256` and `reference_sha256`; else INCOMPLETE with what is missing. A note, never
withholding statistics (Q4). Shown in Results, exported, saved.
**8.4 Saves.** Project: the tab's workspace (peaks, ui, anchors, cc) as today, plus `fitResult: {seal}`
— nothing else authoritative. Spectrum file: `seal` at top level; its convenience arrays (roiBE,
background, fittedY, residuals, peakCurves, statistics) are written FROM the view for external
readers and ignored by the sealed loader. A STALE save keeps the seal and the edited workspace and
reloads STALE. A LEGACY fit re-saves its legacy fields as today (no seal manufactured); `tab.provenance`
(V6.8: the record kept when the reconstruction falls back to peaks only) is saved and loaded and
shown when `fitResult` is null. `.fit.json`: parameters for other data, the record as
`modelProvenance`, support null — the importer unchanged; the saver reads the view (§7).
**8.5 The per-tab workspace context.** `fitMethod` joins the per-tab UI record: `_captureUI` and
`_restoreUI` capture / restore it, both serializers save it in the tab's `ui` record, and a file
without it loads with the page's default ('least_squares'). The method selector gets a change handler
that re-judges the active tab and repaints (as the background controls do). The workspace is never
restored FROM R: a saved edit stays the edit (and loads STALE).
**8.6 Loaders.** ONE function for both formats: `seal` present → schema check (fails → PEAKS-ONLY
with the reason, never a legacy reconstruction) → install `{seal, view}` → PENDING → verify (§9);
the workspace loads as saved and §3 judges it. No seal → the legacy adapter.

## 9. The verification manager

A cache `WeakMap(seal → {softwareAtVerify, result})` (a numerical answer about a seal never expires
with an operation; only its attachment does) and an in-flight map `owner → {seal, attemptId, kind,
op}`. THREE attempt kinds:
- PRODUCER-BOUND — a fresh fit's check after its seal is installed, issued under the fit's existing
  operation token (Run Fit / "Use this solution");
- STAGED — Auto-Fit's two checks, owned by its TRANSACTION (operation token, transaction id, the
  exact staged R / O objects); a reply RESOLVES the transaction when the owner is live and active, the
  operation and transaction are current and the staged objects are those checked; nothing is
  attached or displayed. The commit installs the final seal and enters both answers in the cache (§6.3);
- BACKGROUND — load, activation, undo / history / rollback reinstall, a failed or discarded operation
  that left an earlier seal installed, and the explicit "check again" control; it NEVER claims a fit
  operation (a load must not cancel a running fit).
A PRODUCER-BOUND or BACKGROUND reply is attached only if: the owner is LIVE (still in
`tabManager.tabs`, `_ownerLive`), it still holds that SAME seal, the attempt is the latest for that
owner, and — producer-bound — its operation is still current (`_fitOpCurrent`) AND the owner is still
the ACTIVE tab (`_ownerActive`; `_fitOpCurrent` alone does not see a tab switch). Otherwise it is
discarded and its in-flight entry cleared; a producer-bound attempt discarded by a tab switch is
recovered by `_ensureVerified` (a background attempt) on the next activation. The cache holds the
server's NUMERICAL answers only (consistent / mismatch / unconfirmed); "server unreachable" is not
cached, and "check again" always starts a new attempt.
`_ensureVerified(owner)` runs on every BACKGROUND trigger: if the installed seal has no cached result
and no live attempt, it starts one — so a discarded attempt cannot strand a seal PENDING. Inactive
tabs are verified on load (stack sources included) by background attempts, which a tab switch does
not discard. Unreachable → UNCONFIRMED "server unreachable"
with "check again". The bindings (§2, §3) are re-evaluated at every read; the cache holds only the
server's answer. On a change of a seal's result: the main chart (if its owner is active), Results,
header, R panel, sidebar badges, Quantify, history list; every stack entry whose source holds that seal
has its `_renderDataCache` cleared and a visible stack chart is repainted.

## 10. Visible changes (release-noted; each measured in §12 step 8 on the committed fits)

- χ² shown and exported is the server's; the page formed χ²ᵣ × max(1, n − 3·peaks), wrong with links
  or locks. RMSE and R are the server's.
- The chart, Results, sidebar, Quantify and every export read the fit's RECORDED curves, residuals
  and areas instead of re-evaluating them in the browser (the area FORMULA is already the server's
  since Q5; what changes is that the recorded value is read; differences measured against main).
- A reloaded fit keeps its σ, the lmfit card and its scattered-starts alternatives (O persists).
- Every server fit shows PENDING ("confirming…") until the check returns; UNCONFIRMED offline or when
  the fit was made under other NUMERICS and its recomputation differs (amended 2026-10-15: a deploy
  that changes no fitting math leaves every seal confirmed — the commit is information only), until
  re-run (1d). Support exclusions, σ and Quantify show the recorded values with
  the state; "Use this solution" waits for CURRENT.
- Auto-Fit commits only after both of its fits are confirmed; it rolls back if the check cannot
  confirm them.
- Changing the method selection or the charge-reference settings after a fit makes it stale.
- Saves before this release are never current again (Q1).
- Acceptance labelled "as recorded — not proven"; provenance ATTESTED / INCOMPLETE shown.
- Edit previews no longer clear the stored fit's arrays (the STALE preview is computed beside them).
- Larger saves (full O, alternatives, Auto-Fit evidence; 1b measures the size) and a changed spectrum
  file (a `seal` field).
- The fit method is saved per tab and follows the tab (it used to be one page-wide selector).
- A "check again" control beside an UNCONFIRMED "server unreachable".
- A fit holding a non-bit-stable lineshape (LA) reads UNCONFIRMED (Q7) when its recorded curves are not
  reproduced exactly by this server's evaluation; otherwise it can be CURRENT like any other.
- Uncertainty movement warnings survive a reload (the start is in R); an adopted alternative is judged
  from its own start.
- A history preview draws the snapshot's recorded grid and background, not today's.

## Amendment 2026-10-15 (owner, consistent with Q4): confirmation is by recomputation

A different git commit (or checkout state, or environment) never makes a seal "unconfirmed": it is recorded and
shown as information only. `fitting.verify_fit` ALWAYS recomputes the record; a recomputation that matches is
`consistent` whatever deployment made it. The numerics identity (`NUMERICS_IDENTITY_KEYS`: the numerics version,
the seed derivation, python / numpy / scipy / lmfit / asteval, the machine, the OS release and numpy's BLAS — a
DECLARED compatibility identity, not a proof of identical arithmetic) decides only how a recomputation that
DIFFERS reads: under the same numerics `mismatch` (the record does not hold → STALE), under other numerics
`unconfirmed`, check `numerics`, naming the fields that differ and the failed check (a request this server
cannot read, too). A record not of a response's form — its software record included — is `mismatch` whatever
made it. The open page holds a cached answer only under the numerics the server declares now
(`_cachedVerdict`, `_noteServerSoftware`): other numerics → every installed seal is checked again. An impossible recheck (a non-bit-stable
lineshape's evaluation, a non-finite number, an unreachable server) is `unconfirmed` with its reason as before.
`NUMERICS_VERSION` is bumped by a change to the fitting math and only by one: `scripts/numerics_digest.py`
defines the fitting math (fitting.py without the verifier and the recording, plus app.py's
`_normalise_fit_request` and its helpers, as syntax without docstrings or message text; a refactor that moves no
number is recorded as an `equivalence` entry with its reason) and `tests/test_numerics_version.py` holds it to the
history in `tests/fixtures/numerics_manifest.json`. Tests: `tests/test_seal_1a_verify.py` (a deploy with no
numerics change leaves existing seals confirmed; other numerics recomputing exactly → consistent; differently →
unconfirmed with the reason), `tests/test_browser_seal_step4.py` (the same through the page).
